Lec02 · 提示词与上下文工程

从一句提示词到整个工作上下文

要影响 Agent 的行动，需要组织它每一步决策所见的上下文，并给出可判断的完成条件。 Agent 看到的不只是用户刚输入的话，还包括 harness 的指令与工具说明、AGENTS.md、按需加载的 Skill、历史消息、项目文件和工具输出。提示词工程关注一句话怎样表达；上下文工程关注哪些信息在何时进入工作集，它们来自哪里、适用到哪里、是否仍然有效。

进入上下文不等于获得指令权。代码、网页、论文和测试日志通常是待处理材料或观察结果；不能因为其中写着一条命令，就把它当成用户要求。模型可以描述它认为自己在遵循什么，但这份自述仍要用配置和实际行为核对。命令能否执行，还受到 harness 的审批规则与操作系统权限限制。

把意图变成可判断的完成条件

Intent、Spec 与 Impl 之间有选择空间。没有说清的高影响选择，可能由模型逐项猜定；每一步看似合理，最终仍偏离人的意图。明确要求并非写得越长越好，而是把关键选择和完成条件说清。

一个直接的检验是：**旁观者只看产物和操作结果，能判断通过或不通过吗？**如果不能，Agent 也缺少稳定的停止依据。完成条件应写出交付物、关键约束、检查办法和失败时的报告方式；不能仅凭一段流畅总结宣布完成。

可自动验证的规则与需要人判断的品味，要分别验收。长流程能反复试错的前提是有可信反馈；检查过窄还可能让模型只迎合检查器。

**案例：课堂的八句诗。**藏头、嵌字和押韵可逐项检查，模型也能据此修补；全部通过仍不保证作品自然、好读。这个例子界定了形式检查能证明什么、不能证明什么。

上下文会纠偏，也会污染产物

持续可见的规则有助于纠正偏航，却也占用注意力，并可能把原本只用于沟通的词带进产物。每次遇到问题就往常驻规则里加一句禁令，会使规则越来越长，彼此更难协调。

**案例：否定要求进入注释。**老师要求白色背景、不要半透明效果，模型却把「不要半透明效果」写进代码注释。它说明被禁止的词也进入了上下文，可能影响最终文本。

常驻层适合保存跨任务都成立、遗漏代价高的短规则；当前任务的细节按需提供。能落到类型、检查脚本、测试、CI 或权限边界的要求，应尽量由机制验证。上下文窗口装得下，不代表模型会稳定用好其中每条信息；压缩时保留目标、约束、已验证证据、未决问题和下一步检查，而非按时间复述对话。

[!tip] Insights 历史日志、旧方案和失败尝试可用来追查来路，不能直接充当当前结论。引用实验结果前，核对适用版本、条件和本次证据；无法复核时标明它是历史记录或未验证推断。

用 Agent 学习：立即试，再自己解释

AI 降低了启动一次尝试的成本：没看懂的推导、数据通路或链接过程，可以立刻变成一个小问题，得到例子或运行反馈。但试过不等于学会。合上材料，用自己的话说明，再让 Agent 追问、找反例和验算；卡住的位置正是需要补足理解的位置。

把方法沉淀为 Skill

角色提示主要改变语气与输出样式，不会自动提供任务方法。审稿需要先独立确定问题、替代解释和可能推翻主张的观察，再核对 主张 → 证据 → 假设；否则容易被论文选择的术语、基线和指标锚定。

**案例：让 Agent 扮演审稿人。**如果只给角色和篇幅要求，它能写出像审稿意见的文本，却未必执行上述证据检查。这个差距说明 Skill 应保存方法，而非只保存成品样式。

多次有效的方法可以沉淀为 Skill：保存搜索策略、判断标准、检查点，以及看到什么证据就改变方向，而不是只保存上次答案的版式。Skill 本身也会消耗上下文和指令遵循能力；常驻部分只留目标、硬约束和停止条件，例子与边界情况按需加载。

代码库也是上下文

成熟仓库的命名、分层、错误处理和测试为局部修改提供了现成约束；空项目的许多选择则悬而未决。因此，Agent 接手成熟项目有时比从零建产品更容易。现有代码也可能包含历史缺陷，不能无差别模仿；应辨认哪些约定仍被维护、哪些只是偶然留下的做法。

开放问题需要探索规则

「给我几个方案」只规定了候选数量，没有规定探索是否充分。沿一条路线多想几步，增加的是深度；从不同假设、约束和视角独立寻找候选，增加的是宽度。开放问题还要预先设计如何比较方案：需要什么证据、什么反例、付出什么代价，何时继续搜索。

让不同路线先独立提出可比较的预测，再检查分歧与证据，避免过早围绕第一个看似可行的答案收敛。
