Lec01 · Welcome to GenSE

一句话主线

Agent 大幅降低了把想法变成实现的成本，但软件工程仍须处理意图、规格、实现之间的缺口，以及验证、协作、维护和责任。目标不是让 demo 跑起来，而是让系统在真实约束和变化中持续满足人的意图。

让 Agent 加速实现，用规格和反馈控制方向，用证据判断是否真的完成。

课程主线

1. 作品不再直接证明能力

同一份作业可能出自独立理解，也可能出自一次委托。学习重点因此从「亲手敲完代码」转向：提出值得解决的问题、理解关键原理、设计验收、解释失败、承担取舍。课程鼓励实践和可展示的作品；作品的价值在于别人能运行、质疑、继续使用，而不只是拿到分数。

「禁止古法编程」是课程的挑衅式说法：手写实现不应自动成为学习目标；它不等于不读代码、不理解系统。

2. Agent 是带环境反馈的循环

LLM 可以从使用者角度看作依据 context 预测下一个 token 的模型；流畅输出只说明它在当前上下文里像答案，不能证明正确。Agent 在模型外接上工具和环境，形成循环：

目标与上下文 → 推理/选择动作 → 调用工具 → 观察结果 → 更新上下文 → 下一步

Agent 的实际能力取决于模型，也取决于它能观察什么、操作什么、怎样验证操作结果。Harness 负责承载工具、状态和反馈；长流程还需要重试、恢复与权限边界。把 Agent 当成「更会聊天的搜索框」会浪费这层能力。

3. 把一次成功变成可复用资产

课程中的浏览器办事大厅、邮件处理、装系统、现场造统分工具，展示的是同一条路：让 Agent 探索任务，再把稳定的成功路径沉淀为脚本、工具或工作流。成功一次是演示；可检查、可修改、可重放，才是资产。

计算机专业的优势是能识别更合适的控制面：网页不仅有像素和按钮，也有 DOM、请求和状态；应用名之外还有输入、计算、输出能力。选择语义清楚的接口，会让动作更容易复现和验收。

表单例子：固定点击顺序可能依赖某次页面布局、登录状态和输入数据。可复用流程还应识别目标字段，检查提交前的输入和提交后的状态，并在页面变化、重复提交或失败时给出可处理的结果。

4. Intent → Spec → Impl：最重要的缺口

层次 含义 典型问题
Intent（意图） 人真正想达成的效果，可能连提出者也没想清 「好用」具体对谁、在什么场景？
Spec（规格） 可讨论、可检查的行为与约束 输入范围、兼容性、失败时怎么处理？
Impl（实现） 程序实际做的确定性动作 是否只对示例输入有效？

模型会用猜测填补缺口；不可能每件小事都问，但重大架构、数据表示和验收标准猜错会非常昂贵。通过现有测试，只能说明通过了这些检查；不能证明规格忠实表达了真实意图。

二维码 Excel 案例中，硬编码版本能演示，却没有实现「不同输入都成立」的计算过程；后续增加需求时难以局部修改。转折点是先设计可复用的公式与工作表结构，再让输入长度影响数据量和帧数，而非复制整套算法表达。这是架构问题，不是再多生成一些内容就能解决的问题。

5. 软件工程让错误早出现、影响小、回退便宜

拆解不确定性 → 做最小可验证实验 → 建立检查与门控 → 小步迭代 → 更新规格

例如二维码工具可以先验证「短字符串 → 单帧二维码 → 独立解码器读回原文」，再逐步加编码、分片、拼接、刷新和兼容性。每一步消除一种未知。生产速度提高后，验证、接口、可观测性和维护性更容易成为瓶颈；生成很多代码不等于做成了工程。

我的实践原则：怎样更好地使用 Codex

  1. 先给真实目标和边界。 说清楚谁使用、要解决什么、已有代码/笔记在哪里、不能破坏什么；不要只给一个实现指令。
  2. 让验收可观察。 指定可运行的检查、预期现象、失败样例或需要人工判断的标准。要求报告已验证的证据与仍未验证的部分。
  3. 按决策代价分工。 低影响、易回滚的细节让 Agent 自行决定并验证；高影响、难回滚的产品/架构选择先比较方案或做小实验。
  4. 一次交付一个可检查的增量。 让 Agent 读现状、修改、验证、总结差异；一条成功路径稳定后，再沉淀成脚本、skill 或文档。
  5. 保留人的主动学习。 可以先让 Agent 做出可观察的系统，再追问关键机制；对需要掌握的概念，用自己复述、反例和独立检查验收理解。漂亮摘要不能代替学习。

一个可复用的任务表述：

目标是___，使用者/场景是___。请先检查___中的现状，指出影响方案的关键未知；对可逆细节自行决定，对高代价选择给出依据。完成一个最小可验证增量，用___验收，并区分已验证事实、推断和未验证风险。

需要警惕的边界

  • 「单步 99% 成功，100 步全成功约 36.6%」只在各步成功率相同且相互独立的简化假设下成立；它说明长流程需要检查和恢复，不能直接当作实际 Agent 的成功率。
  • 「实现不再稀缺」「验证成为瓶颈」是课程对成本变化的判断，不代表所有任务都能低成本生成或自动验收。关键要看任务边界、反馈质量和错误代价。
  • 人的责任要与决策权、停止权和可获得的证据相匹配；只让人对无法检查的自动化结果背锅，不是好的协作设计。
